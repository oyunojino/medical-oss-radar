# 카카오톡 피드백(`이것은피드백.pdf`) 대응 정리

피드백 파일이 지적한 문제는 크게 3가지였습니다. 결론부터 말하면 **1번과 3번은 해결됐고, 2번(VEX 판정 로직)은 일부만 진행된 상태**입니다. 아래에 하나씩, 전문 용어를 최대한 풀어서 설명합니다.

| # | 피드백 내용 | 상태 |
|---|---|---|
| 1 | 취약점 개수 정리 (중복 제거 / dev 의존성 필터링) | ✅ 해결 |
| 2 | VEX 판정 로직 (affected / not_affected 가르기) | 🟡 부분 진행 — 설계 논의 아직 필요 |
| 3 | GitHub API 429 (에러 때문에 활동 정보 비어있음) | ✅ 해결 |

---

## 1. 취약점 개수 정리 — ✅ 해결

### 문제가 뭐였나

대시보드에 "취약점 6,336건"이라고 떴는데, 이 숫자는 부풀려져 있었습니다. 이유는 두 가지였어요.

- **같은 취약점이 여러 번 세어짐**: 하나의 보안 취약점에는 이름이 여러 개 붙을 수 있습니다. 예를 들어 같은 문제가 `CVE-2022-1234`(정부 표준 이름)로도 불리고 `GHSA-xxxx`(GitHub 자체 이름)로도 불리는데, 이걸 프로그램이 서로 다른 취약점처럼 각각 세고 있었습니다.
- **실제 배포되지 않는 코드까지 포함됨**: 프로젝트를 만들 때 "테스트할 때만 쓰는 도구"와 "실제 서비스에 들어가는 코드"가 섞여서 관리됩니다(예: 테스트 프레임워크는 개발자 컴퓨터에서만 실행되고, 실제 사용자에게 배포되는 프로그램 안에는 안 들어감). 이런 테스트/빌드 전용 도구에 취약점이 있어도 실제 공격 대상이 될 수 없는데, 기존 코드는 이걸 구분하지 않고 다 세고 있었습니다.

### 어떻게 고쳤나

- **취약점 이름 통합** (`lib/osv.ts`): CVE, GHSA 등 여러 이름이 같은 취약점을 가리키면 하나로 묶고, "(취약점, 부품, 버전)"이 완전히 같은 것만 하나로 셉니다. 여러 프로젝트가 같은 부품을 쓰고 있어도 전체 합계에서는 중복 없이 계산합니다.
- **개발용 도구 걸러내기** (`scripts/dev-scope.mjs` 신규 작성): 프로젝트의 의존성 목록 파일(npm의 `package-lock.json`, Python의 `Pipfile.lock` 등)을 읽어서, 어떤 부품이 "테스트/빌드 전용"인지 자동으로 표시합니다. 단, **모든 파일이 동시에 "이건 개발용"이라고 동의할 때만** 제외합니다 — 조금이라도 애매하면 실제 취약점 집계에 그대로 남겨서, 안전한 쪽(더 엄격하게 세는 쪽)으로 판단합니다.

### 결과

수정 전후로 SBOM과 취약점 데이터를 전부 다시 만들어서 반영했습니다.

**취약점 합계: 6,336건 → 5,185건** (커밋 `dff3886`)

이 숫자는 이제 "실제로 배포되는 코드에, 중복 없이 존재하는 취약점"만 센 것이라 논문·발표에 쓰기에 훨씬 안전합니다.

## 2. VEX 판정 로직 — 🟡 부분 진행 (설계 논의 아직 필요)

### 먼저 용어 정리

- OSV(취약점 데이터베이스)가 하는 일은 딱 "이 버전의 이 부품에는 이 취약점(CVE)이 있다"까지입니다. 그 취약한 코드가 **실제로 실행되는지**는 안 알려줍니다.
- **VEX**는 그 다음 단계로, "이 취약점이 우리 프로젝트에 실제로 영향을 주는지"를 판정하는 절차입니다. 상태는 4가지: 아직 조사 안 함(`under_investigation`), 영향 있음(`affected`), 영향 없음(`not_affected`), 이미 고쳐짐(`fixed`).
- 피드백은 `not_affected`(영향 없음)로 판정하는 근거가 표준상 5가지이고, 쉬운 것부터 어려운 순서라고 설명했습니다:

| 근거 | 쉬운 설명 | 난이도 |
|---|---|---|
| 컴포넌트 자체가 없음 | 그 라이브러리를 아예 안 씀 | 쉬움 |
| 취약한 코드가 안 들어감 | 라이브러리는 쓰지만, 문제의 그 함수는 빠진 버전 | 중간 |
| 실행 경로에 없음 | 코드는 있지만 프로그램이 그 부분을 절대 실행 안 함 | 어려움 |
| 공격자가 조종 못 함 | 실행은 되지만 외부에서 입력을 못 건드림 | 더 어려움 |
| 이미 다른 방어책이 막음 | 설정 등으로 이미 차단되어 있음 | 거의 수동 확인 |

### 지금까지 만든 것 (`npm run vex`, `scripts/vex-scan.mjs`)

이 중 **딱 하나, "취약한 코드가 안 들어감"만 자동화**했습니다. 방식은:

1. 그 취약점을 고친 커밋(수정 내역)을 찾아서, 어떤 함수 이름이 바뀌었는지 뽑아냅니다.
2. 실제로 우리가 쓰고 있는 버전의 소스 코드를 통째로 내려받습니다.
3. 그 함수 이름이 소스 코드 안에 하나도 없으면 → "영향 없음"으로 표시합니다.
4. 조금이라도 애매하면(코드를 찾을 수 없거나, 함수가 있거나, 압축된 코드라 확인이 안 되거나 등) → 무조건 "조사 중"으로 남깁니다. **의료 소프트웨어 공급망 데이터라서, 틀리게 "안전하다"고 하는 것이 "아직 확인 안 됨"이라고 하는 것보다 훨씬 위험하다는 원칙**을 지켰습니다.

### 아직 안 된 것 — 왜 "부분 진행"이라고 부르나

- **나머지 4가지 근거는 자동화하지 않았습니다.** 특히 "실행 경로에 없음"(콜 그래프 분석)과 "공격자가 조종 못 함"(데이터 흐름 분석)은 피드백에서도 "언어마다 도구가 다르고 특히 DICOM 같은 C/C++ 코드가 까다롭다"고 언급한 부분인데, 이번 작업 범위에는 포함되지 않았습니다.
- **`affected`(영향 있음) 판정은 아예 만들지 않았습니다.** 지금 코드는 "영향 없음"을 증명하지 못하면 전부 "조사 중"으로 남겨둘 뿐, 적극적으로 "영향 있음"이라고 판정하는 로직은 없습니다.
- **판정 단위 문제도 아직 안 풀렸습니다.** 피드백이 지적한 대로, OSV/VEX는 "부품 단위"로 결과가 나오는데 우리가 정말 원하는 결론은 "이 프로젝트(레포) 전체가 이 취약점에 영향받는가"입니다. 같은 취약 부품이 프로젝트 안에서 여러 경로로 들어올 수 있는데, 그중 하나라도 실행되면 영향 있음으로 볼지, 다 확인해야 영향 없음으로 볼지 — 이 규칙은 아직 코드로 정해지지 않았습니다.
- **실제로 돌려본 프로젝트도 아직 2개뿐입니다** (`metriport`, `repmode` — 취약점 534건 검사, 그중 "영향 없음"으로 확정된 건 0건). 이건 코드가 잘못됐다는 뜻이 아니라, 피드백에서도 예측했듯 "대부분은 실제로 그 취약한 함수가 진짜 남아있다"는 게 자연스러운 결과입니다. 다만 아직 대시보드에 등록된 203개 프로젝트 전체를 대상으로 돌린 적은 없습니다.

### 정리

이 항목은 피드백에서도 "같이 설계부터 얘기해야 한다"고 명시한 부분이라, 지금 상태는 "**5가지 근거 중 1가지를 자동화하는 시험판을 만들어서 방향성을 확인한 단계**"입니다. 프로젝트(레포) 단위로 결론 내는 규칙, 콜 그래프/데이터 흐름 분석 도구 선택, `affected` 판정 로직은 다음 설계 논의에서 다룰 부분으로 남아 있습니다.

## 3. GitHub API 429 에러 — ✅ 해결

### 문제가 뭐였나

대시보드가 각 프로젝트의 별(star) 개수, 최근 커밋 시각 같은 정보를 GitHub에서 실시간으로 가져오는데, 203개 프로젝트 중 148개가 이 정보 없이 비어 있었습니다. 원인은 GitHub에 너무 많은 요청을 한꺼번에 보내서 "요청이 너무 많다(429 에러)"며 차단당한 것이었습니다. 로그인 없이 GitHub API를 부르면 시간당 60번까지만 허용되는데, 프로젝트가 203개라 순식간에 한도를 넘겼습니다.

### 어떻게 고쳤나

1. **요청 방식 개선** (`lib/github.ts`의 `fetchAllRepoStats`): 프로젝트마다 하나씩 따로 요청하던 것을, 인증 토큰이 있을 때는 여러 레포를 한 번에 묶어서 요청하는 방식(GraphQL)으로 바꿨습니다. 토큰이 없을 때를 위한 예비 경로도 동시 요청 개수를 제한해서 덜 공격적으로 만들었습니다.
2. **인증 토큰 등록**: GitHub 개인 액세스 토큰(비밀번호 같은 것, 공개 저장소 정보만 읽는 권한)을 발급받아 로컬 개발 환경(`.env.local`)과 실제 배포 서버(Vercel) 양쪽에 등록했습니다. 토큰이 있으면 시간당 한도가 60번 → 5,000번으로 늘어납니다.
3. **깨진 저장소 주소 수정**: 토큰을 넣은 뒤에도 남아있던 일부 "정보 없음" 항목을 조사해보니, 3개는 저장소가 다른 곳으로 이사가서 주소가 틀렸던 것이었습니다(예: `LabKey/labkey-server` → `LabKey/server`). 실제 새 주소를 찾아 고쳤습니다.

### 결과

**203개 프로젝트 전부 정상적으로 활동 정보를 가져옵니다** (이전: 148개 누락 → 이후: 전체 커버, 남은 4개는 애초에 GitHub 저장소가 없는 프로젝트라 정상). 자세한 조사 과정은 [`github-data-integrity.md`](./github-data-integrity.md) 문서에 더 자세히 남겨뒀습니다.
